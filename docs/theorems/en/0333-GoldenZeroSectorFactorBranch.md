# 0333 — `GoldenZeroSectorFactorBranch`

## Declaration kind

This declaration is not a theorem but an **`inductive`** type.

It defines the two-adic case split arising in zero-sector factorization as a finite type with three constructors.

```lean
/-- The exhaustive two-adic branch label. -/
inductive GoldenZeroSectorFactorBranch
  | odd
  | evenLeftLow
  | evenRightLow
  deriving DecidableEq
```

## Lean type

After the declaration, Lean has a new type

```lean
GoldenZeroSectorFactorBranch : Type
```

and three constructors

```lean
GoldenZeroSectorFactorBranch.odd : GoldenZeroSectorFactorBranch
GoldenZeroSectorFactorBranch.evenLeftLow : GoldenZeroSectorFactorBranch
GoldenZeroSectorFactorBranch.evenRightLow : GoldenZeroSectorFactorBranch
```

In addition,

```lean
deriving DecidableEq
```

automatically provides decidable equality for branch values.

Thus propositions such as

```lean
b = .odd
```

can be treated as computable decisions, and downstream theorems can receive branch equality as a hypothesis and eliminate incompatible constructors with `cases` or `simp`.

## Mathematical meaning

This declaration itself does not assert a new number-theoretic theorem.

Its role is to provide a **finite label type** for the three placements of two-adic valuation that occur after zero-sector inversion and during factorization.

The constructors have the following intended meanings.

### `odd`

This is the odd-side branch.

In the immediately following constructor `GoldenZeroSectorFactorData.odd`, natural numbers $e,f$ satisfy

$$
A_0 = 2e^5,
\qquad
B_0 = 2f^5,
$$

with both $e$ and $f$ odd.

The factor difference then yields

$$
e^5 + 4d^5 = f^5,
$$

so the preceding theorem `eleven_dvd_d_of_fifth_add_four_fifth` supplies the mod 11 obstruction for this branch.

### `evenLeftLow`

This labels the even-side branch in which the left factor $A_0$ carries the relatively lower two-adic exponent.

The corresponding factor datum records

$$
A_0 = 8e^5,
\qquad
B_0 = 16f^5.
$$

### `evenRightLow`

This is the left-right mirror branch. The corresponding factor datum records

$$
A_0 = 16e^5,
\qquad
B_0 = 8f^5.
$$

The important point is that these equations and parity conditions are **not fields of this `inductive` declaration itself**. This type stores only the names of the branches. The actual number-theoretic certificate data is stored in the next declaration, `GoldenZeroSectorFactorData`.

## Role in the full proof

This declaration sits at the boundary between the zero-sector inversion packet and the complete factor packet, converting a number-theoretic two-adic case split into a **finite state at the type level**.

By this point, `GoldenZeroSectorInversionPacket` already packages data such as

- factor product,
- factor difference,
- coprimality,
- parity,
- positivity of the natural factors.

The immediately preceding developments also establish

- `odd_factor_halves`,
- `coprime_Q_d`,
- `fifth_mod_eleven_cases`,
- `eleven_dvd_d_of_fifth_add_four_fifth`,

which provide the local lemmas needed to analyze the odd and even branches.

`GoldenZeroSectorFactorBranch` lets all later APIs refer to the outcome using the three states

```text
odd / evenLeftLow / evenRightLow
```

instead of leaving the distinction as an ephemeral `by_cases` split or nested disjunction inside a proof script.

The next declaration, `GoldenZeroSectorFactorData`, has constructors matching these three labels one-for-one and attaches fifth-power factorizations, coprimality, ownership, parity, and branch-specific difference equations.

Thus this declaration promotes the arithmetic case split into an explicit **branch vocabulary** reusable by downstream APIs.

## Lean-specific processing

### Exhaustiveness is encoded by the inductive type

Because this is an `inductive` type, values other than the three constructors cannot be formed.

Hence the statement that the three branches are exhaustive does not need a separate theorem; it is built into the elimination principle of the type.

### Automatic `DecidableEq`

The branch type is a finite constructor type with no payloads, so equality is mechanically decidable.

Downstream proofs can therefore use abbreviated constructors such as `.odd` together with simplification of branch equality.

### Separation of labels from arithmetic certificates

The type does not carry $e,f$ or factorization equations directly. Those are delegated to the dependent inductive type `GoldenZeroSectorFactorData p`.

This separates APIs that only need a branch name from APIs that need the full proof witnesses.

## Redundancy and duplication

The declaration is close to minimal, so there is almost no code-level redundancy.

The three constructor names are repeated by the three constructors of the following `GoldenZeroSectorFactorData`. Superficially this is duplication, but it is intentional. It permits the projection

```lean
GoldenZeroSectorFactorData.branch
```

to be written naturally as

```lean
| .odd .. => .odd
| .evenLeftLow .. => .evenLeftLow
| .evenRightLow .. => .evenRightLow
```

This is therefore design-level duplication that makes the correspondence between the label layer and the certificate-data layer explicit, rather than redundancy that should obviously be removed.

## Optimization candidates

### 1. Replacing it with `Fin 3` or another generic finite type is not attractive

The same three states could technically be represented by `Fin 3`, but that would erase the mathematical meaning carried by the names `odd`, `evenLeftLow`, and `evenRightLow`.

The dedicated `inductive` type is substantially more readable.

### 2. Possibly derive `Repr`

If debugging or `#eval` output of branch values becomes useful, deriving `Repr` could be considered.

No such need is established by the present proof API, where `DecidableEq` is the important derived instance.

### 3. Do not merge the branch label and full proof data without a clear benefit

One could design an indexed inductive type in which the branch itself carries all invariants. However, the immediately following `GoldenZeroSectorFactorData` already fulfills that role.

The current two-layer design — a lightweight label type plus a heavyweight dependent certificate type — is structurally clean.

## Comparator challenge suitability

**Low to medium as an isolated proof challenge, but good as an API-design challenge.**

The declaration itself is only a three-constructor enumeration, so there is little proof search to compare. A design Comparator could instead compare:

1. the current dedicated `inductive` label type,
2. omitting the label and branching only on `GoldenZeroSectorFactorData` constructors,
3. using a generic finite type such as `Fin 3`,
4. merging branch labels and factor proof data into one indexed structure or inductive type.

Useful evaluation axes would include readability of pattern matching, downstream theorem types, `simp` behavior, separation between state labels and proof data, and maintainability if more branches are introduced later.

In particular, because the current design inserts the explicit projection `GoldenZeroSectorFactorData.branch`, the key Comparator question is whether an independent branch-label type pays for itself in the downstream API.
