# 0163 — `goldenConj`

## Lean type

```lean
/-- The nontrivial conjugation `a+b*φ |-> (a+b)-b*φ`, induced by `φ |-> 1-φ`. -/
def goldenConj (x : GoldenInt) : GoldenInt := ⟨x.fst + x.snd, -x.snd⟩
```

This is a `def`, not a theorem. It defines the nontrivial conjugation on the golden-integer ring `GoldenInt` directly in coordinates.

## Mathematical statement and meaning of the declaration

Read an element of `GoldenInt` as

$$
x=a+b\varphi
$$

with the generator satisfying

$$
\varphi^2=\varphi+1.
$$

The other root of the same quadratic equation is

$$
\varphi'=1-\varphi,
$$

so conjugation acts by

$$
a+b\varphi\longmapsto a+b(1-\varphi).
$$

Rearranging gives

$$
a+b(1-\varphi)=(a+b)-b\varphi,
$$

hence the coordinate transformation in the basis `1, φ` is

$$
(a,b)\longmapsto(a+b,-b).
$$

The Lean definition

```lean
def goldenConj (x : GoldenInt) : GoldenInt :=
  ⟨x.fst + x.snd, -x.snd⟩
```

implements exactly this transformation.

## Role in the overall proof

After 0161 `goldenPhi` and 0162 `goldenOfInt` make the two basis directions of the golden order explicit, 0163 introduces the nontrivial quadratic conjugation on that basis.

This conjugation becomes central together with the following `goldenNorm`. Downstream source proves, among other facts,

- `goldenConj goldenPhi = goldenSub goldenOne goldenPhi`;
- `goldenConj (goldenOfInt a) = goldenOfInt a`;
- `goldenConj (goldenConj x) = x`;
- `goldenConj (goldenMul x y) = goldenMul (goldenConj x) (goldenConj y)`;
- `goldenNorm (goldenConj x) = goldenNorm x`;
- `goldenMul x (goldenConj x) = goldenOfInt (goldenNorm x)`.

`GoldenDivisibility.lean` later also develops compatibility of conjugation with addition, negation, subtraction, and powers. Thus this declaration is not merely a coordinate transform: it is the entry point for the symmetry used by norm multiplicativity, unit arguments, divisibility, and the Euclidean-domain development.

## Direct dependencies

The immediate dependencies are mainly:

- `GoldenInt`;
- `GoldenInt.fst`;
- `GoldenInt.snd`;
- integer addition;
- integer negation.

No theorem is required for the construction itself; the result is specified directly by a structure literal.

Semantically, 0161 `goldenPhi` and 0162 `goldenOfInt` are also important. The former identifies the nontrivial basis element `φ`, while the latter identifies the integer subring fixed by conjugation, making `goldenConj` readable as the map that fixes integers and sends `φ` to `1-φ`.

## Proof / construction flow

There is no proof script.

```lean
def goldenConj (x : GoldenInt) : GoldenInt :=
  ⟨x.fst + x.snd, -x.snd⟩
```

is the complete construction.

Mathematically it performs

$$
a+b\varphi
\longmapsto
(a+b)-b\varphi.
$$

The first coordinate receives the old second coordinate, and the second coordinate changes sign.

## Lean-specific processing

`GoldenInt` is a structure with two integer fields, so Lean infers the constructor of `⟨x.fst + x.snd, -x.snd⟩` from the expected type.

A key design point is that `goldenConj` is not initially packaged as a `RingHom` or an equivalence. It is first introduced as a raw coordinate function, with properties such as

```lean
theorem goldenConj_invol ...
theorem goldenConj_mul ...
```

proved separately afterward.

This keeps the coordinate semantics fully visible and lets later properties reduce through `ext <;> simp [goldenConj]` and `ring`. The trade-off is that the abstract statement “conjugation is an involutive ring automorphism” is distributed across several individual theorems rather than bundled in a single algebraic structure.

## Redundancy and duplication

The definition itself is essentially minimal. However, downstream declarations include separate compatibility theorems such as

- `goldenConj_add`;
- `goldenConj_neg`;
- `goldenConj_sub`;
- `goldenConj_mul`;
- `goldenConj_pow`;
- `goldenConj_invol`.

Abstractly, these are pieces of the single statement that conjugation is an involutive ring automorphism. The separation is therefore a potential structural duplication, but it is also consistent with the explicit-coordinate style of the FLT5 development: each property remains auditable as a concrete coordinate identity.

## Optimization candidates

1. Keep the current raw coordinate function and accumulate individual compatibility theorems.
2. Bundle additive, multiplicative, and unit preservation into a `RingHom GoldenInt GoldenInt`.
3. Package involutivity as a ring equivalence `GoldenInt ≃+* GoldenInt`.
4. Introduce a generic quadratic-order abstraction in which conjugation is generated by exchanging the two roots of the quadratic polynomial.
5. Recast the construction through `AdjoinRoot` or quadratic-algebra infrastructure and reuse an existing conjugation API where appropriate.

The current one-line definition is maximally transparent. Any optimization should therefore be judged by downstream theorem reuse and integration with generic algebra APIs, not merely by reducing local line count.

## Required Mathlib imports and import optimization

The standalone artifact uses `import Mathlib`. In isolation, `goldenConj` requires only the definition of `GoldenInt` together with integer addition and negation; it invokes no advanced Mathlib theorem directly.

The complete `GoldenOrder` module also uses `Zsqrtd`, `ring`, `omega`, `norm_num`, and substantial typeclass infrastructure, so the true minimal import set must be determined at module level. No Lean build is performed in this museum pass, so import reduction is recorded only as an optimization candidate.

/-- The integral norm `N(a+b*φ)=a^2+a*b-b^2`. -/
