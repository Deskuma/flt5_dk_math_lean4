## Mathematical statement

`SignedFiveAdicSource u v w carrier residual distinguished` is a provenance proposition recording from which of the two signed orientations the triple

$$
(carrier, residual, distinguished)
$$

stored in the common five-adic packet originates.

The `difference` constructor represents

$$
carrier=w-v,
\qquad residual=GN5(w-v,v),
\qquad distinguished=u,
$$

while the `sum` constructor represents

$$
carrier=u+v,
\qquad residual=SumGN5(u,v),
\qquad distinguished=w.
$$

The declaration itself proves no new arithmetic fact. It is a tagged proposition preserving the origin of the data after two representationally different branches have been mapped to the same `carrier/residual/distinguished` interface.

## Role in the full proof

By 0073, the arithmetic ingredients are ready to show in either orientation that the residual has $5$-adic valuation $1$ and the carrier has $5$-adic valuation $4\pmod5$. The next task is to package those facts into one common packet.

`SignedFiveAdicSource` becomes the provenance field of that packet. The following `SignedFiveAdicPacket` contains

```lean

```

and `nonempty_signedFiveAdicPacket_of_normalForm` constructs it in the difference branch as

```

```

Thus later layers can use common arithmetic invariants while still being able, if necessary, to recover by pattern matching whether a packet came from the difference or sum orientation.

## Declaration flow

There is no proof body beginning with `:= by`. Instead, two constructors specify the formation rules for provenance.

1. Fix common parameters `u v w carrier residual distinguished : ℕ`.
2. The `difference` constructor requires three equalities identifying the carrier with `w - v`, the residual with `GN5 (w - v) v`, and the distinguished variable with `u`.
3. The `sum` constructor requires three equalities identifying the carrier with `u + v`, the residual with `SumGN5 u v`, and the distinguished variable with `w`.
4. Either constructor yields the same proposition `SignedFiveAdicSource ...`.

Thus this is best read not as a proof flow but as a data-provenance formation rule generated by two constructors.

## Lean-specific processing

### `inductive ... : Prop`

`SignedFiveAdicSource` lives in `Prop`, not in `Type`. Its purpose is therefore not to retain a computational branch tag but to retain logical evidence that the triple arose from one of the two valid orientations.

### Equalities inside constructors

The constructors do not redefine the values internally. Instead they require externally supplied `carrier`, `residual`, and `distinguished` values to equal the appropriate orientation-specific expressions. This lets the common packet use orientation-independent field names.

### `.difference rfl rfl rfl` / `.sum rfl rfl rfl`

The later packet builder chooses the values to be exactly the expressions expected by each constructor, so all three identifications close by `rfl`. This is a lightweight use of dependent constructors for provenance tracking.

## Redundancy and duplication

The `difference` and `sum` constructors have visibly parallel shapes, each listing three equalities. That duplication appears intentional because it makes the orientation map explicit.

At the same time, making `carrier`, `residual`, and `distinguished` external parameters and then requesting three equalities in each constructor is somewhat verbose. Other designs could existentially generate the triple inside each constructor or use an orientation-specific record. The current design, however, fits the common fields of `SignedFiveAdicPacket` very well.

## Optimization candidates

1. Generalize `SignedFiveAdicSource` into a relation derived directly from `SignedBranchAOrientation`, centralizing the orientation mapping in one place.
2. Replace the three equalities by a product equality or a small record. This may be shorter, although the current separate equalities are likely easier to rewrite with.
3. Audit whether the provenance `source` field is ever eliminated later. If it is never used, removal could be considered; the currently inspected material is insufficient to assert that, so this remains only a candidate.
4. The constructor names `difference` and `sum` are concise, but names reflecting `SignedBranchAOrientation.differenceGap` and `.sumGap` could make the correspondence even more explicit.

## Comparator challenge suitability

**Low as a standalone proof challenge.**

There is almost no proof search here; the interesting comparison is API design. It could, however, serve well as a design comparator: “Design a provenance type that unifies two orientations into one common packet.”

Possible designs include:

- the current `inductive ... : Prop` plus three equalities,
- an orientation tag with dependent functions determining the values,
- a sum type of orientation-specific records,
- no provenance at all, retaining only arithmetic invariants in the packet.

Useful criteria are constructor simplicity, ease of rewriting, recoverability of branch information, and how effectively the packet interface is unified.
